# Как подключить скиллы ко всем репозиториям

Проверено по документации 2026-10-10. Это описание механизма и план раскатки; остальные репозитории автоматически не изменяются.

## Каталоги обнаружения

- Codex: проектный `.agents/skills/`, пользовательский `~/.agents/skills/` ([документация](https://learn.chatgpt.com/docs/build-skills)).
- Cursor: проектный `.agents/skills/` или `.cursor/skills/`, глобальный `~/.agents/skills/` или `~/.cursor/skills/` ([документация](https://cursor.com/docs/skills)).
- Claude Code: `.claude/skills/` в проекте, `~/.claude/skills/` для пользователя ([документация](https://code.claude.com/docs/en/skills)). Это не универсальная установка для всех продуктов Claude.
- Antigravity 2.0 и IDE: `.agents/skills/` в workspace, `~/.gemini/config/skills/` глобально. CLI использует другой глобальный путь `~/.gemini/antigravity-cli/skills/`; для CLI используйте проектный режим ([документация](https://antigravity.google/docs/skills)).

Установщик выбирает `.agents/skills/` для первых трёх совместимых агентов и `.claude/skills/` для Claude. Глобальный режим рассчитан на Antigravity 2.0/IDE. Native-пути важнее упоминания URL в AGENTS.md.

## Одна локальная машина

Один clone каталога, затем `python3 scripts/install.py --user`. Скиллы становятся доступны в локальных проектах этого пользователя при запуске агента. Обновлять явно: получить проверенную версию через Git и повторить установку. Зафиксируйте checkout на SHA, если нужна воспроизводимость.

Это делает скиллы доступными и за пределами Beoma. Если нужен выбор скиллов только для конкретных проектов, используйте `--project`, а не глобальную установку.

## Команда, независимые репозитории и worktree

В каждый репозиторий-потребитель добавьте один onboarding/setup шаг, выполняемый **до запуска сессии**. Он скачивает одобренный SHA и запускает установщик из этого checkout. Пример команды для setup-скрипта:

```sh
# BEOMA_SKILLS_SHA — полный SHA проверенного коммита, хранится в конфиге проекта.
# BEOMA_PROJECT_ROOT — корень checkout потребителя.
# Подготовьте аутентификацию Git для доступа к приватному источнику.
set -eu
: "${BEOMA_SKILLS_SHA:?Set approved commit SHA}"
: "${BEOMA_PROJECT_ROOT:?Set consumer repository root}"
beoma_skills_tmp=$(mktemp -d)
trap 'rm -rf "$beoma_skills_tmp"' EXIT
git clone https://github.com/elementary1997/beoma-skills.git "$beoma_skills_tmp/catalog"
git -C "$beoma_skills_tmp/catalog" checkout --detach "$BEOMA_SKILLS_SHA"
python3 "$beoma_skills_tmp/catalog/scripts/install.py" --project "$BEOMA_PROJECT_ROOT"
```

Каждый worktree — отдельный потребитель: установите в его корень или храните копии в Git. Инструкция в AGENTS.md может напоминать о setup и выборе скиллов, но не гарантирует загрузку отсутствующего файла в уже запущенную сессию. При изменении каталога проверьте список скиллов и при необходимости перезапустите сессию.

Для нового репозитория включите этот шаг в используемый шаблон/setup. Для существующих — отдельная небольшая миграция после пилота. GitHub organization сама не распространяет локальные skill-каталоги на агенты, SSH-хосты и машины разработчиков.

## Облако и окружения без доступа к источнику

Глобальные файлы локальной машины не считать доступными удалённой сессии. Варианты:

1. Setup окружения клонирует приватный каталог с доступом только на чтение и устанавливает его до запуска агента. Авторизацию Git задаёт окружение, не скилл и не Git-файлы.
2. Установленные `.agents/skills/` и `.claude/skills/` коммитятся в приватный репозиторий-потребитель. Вместе с ними сохраняйте `.beoma-skills-state.json`: он содержит SHA источника и хеши, секретов не содержит. Тогда повторная установка отличает управляемые копии от чужих. Не добавляйте эти файлы в публичный репозиторий без разрешения на публикацию содержимого.

Если копии локальные, добавьте эти два каталога и state-файл в `.gitignore` или локальный `.git/info/exclude`. Установщик сам ignore и инструкции потребителя не меняет.

Cursor предлагает отдельную синхронизацию `~/.cursor/skills/` для Cloud Agents; наш глобальный режим туда не пишет. Проектная установка устраняет зависимость от этой функции. Для cloud Claude Code документация описывает загрузку закоммиченных `.claude/skills/`; локальный `~/.claude/skills/` туда не переносится.

## Версии, конфликты и обновления

State-файл фиксирует SHA, но не скачивает обновления. Нельзя тихо заменять проверенную версию на `main` в начале каждой сессии. Обновление — новый одобренный SHA, установка, smoke-test и изменение pin в потребителях.

Установщик проверяет конфликты всех выбранных каталогов до записи, отказывается менять чужие/локально изменённые скиллы и не поддерживает `--force`. При конфликте сохраните изменения и решите вручную, что является каноном. Удалённые из источника или невыбранные скиллы не удаляются автоматически. Для удаления уберите только известные управляемые папки и соответствующие записи state вручную.

Копирование нескольких папок не является единой файловой транзакцией. После прерывания/ошибки диска проверьте копии и state; не обходите защиту без сохранения нужных данных. `--allow-dirty` предназначен для локальной разработки, записывает SHA с `+dirty` и не даёт воспроизводимую версию для команды.

## Пилот и раскатка

1. Два репозитория: UI-приложение и проект без UI. Проверить discovery и отсутствие лишнего применения UI-скилла.
2. В четырёх агентах проверить вызов `beoma-ui-review`, чтение references, работу по скриншоту и живому URL. Инструменты браузера проверяются отдельно: формат скилла не устанавливает их.
3. На одном экране сравнить замечания с ручной QA; убрать ложные срабатывания. Фиксировать версии агентов и проверенные состояния.
4. После успешного пилота включить pinned setup в шаблон новых проектов и мигрировать существующие. Обновления раскатывать явно; контроль в CI может проверять наличие скилла и ожидаемую запись SHA.

Реальная совместимость загрузки и качество UI-ревью требуют этого пилота; тесты установщика подтверждают доставку файлов, а не поведение четырёх агентов.
