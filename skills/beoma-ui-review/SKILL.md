# Глубокая проверка и исправление UI

Результат — подтверждённые находки, интерактивный чек-лист, исправления и доказательства повторной проверки. Сохраняй язык дизайна продукта. Эстетические предпочтения отделяй от дефектов.

## 1. Определи объект, эталон и доступ

Прочитай инструкции проекта и команды запуска. Определи тип: лендинг, фронтенд сервиса или оба. Найди доступные URL, код, макеты, дизайн-систему, целевую аудиторию, основной CTA/сценарий и поддерживаемые устройства. При заданном URL начинай с него. Если обязательный объект/эталон отсутствует, запроси его, продолжая независимые проверки. Без макета не обещай точное соответствие макету; без аналитики не обещай прирост конверсии.

По умолчанию выполняй **аудит → интерактивный чек-лист → исправления → повторная проверка**. Явные «только ревью», «не меняй код», «сначала покажи план» ограничивают этот цикл. Применение скилла разрешает необходимые локальные обратимые исправления подтверждённых дефектов. Оно не разрешает публикацию, оплату, удаление реальных данных или изменение внешних аккаунтов. Если есть только URL/скриншот, заверши доступный аудит и чек-лист; без исходников не притворяйся, что исправил систему.

## 2. Составь карту покрытия

Прочитай [методику глубокой проверки](references/deep-audit.md) и [визуальный чеклист](references/checklist.md). Выбери применимые модули. Для лендинга проверь всю страницу и путь к целевому действию; для сервиса — ключевые маршруты, общий shell и состояния основных компонентов. Зафиксируй проверенные URL, браузер/версию, размеры viewport в CSS px, окружение, сценарии и ограничения.

У каждого пункта покрытия есть результат `pass`, `fail`, `not_checked` или `not_applicable`, описание и доказательство/причина. Доступный модуль не пропускай молча. Разворачивай состояния и пограничные случаи по риску; глубина — наблюдаемое покрытие, а не число замечаний. Не заявляй проверку всей системы по выборке экранов.

Используй доступные инструменты браузера по их собственным инструкциям. Не выдумывай MCP, доступ к экрану, Playwright или Lighthouse. Переиспользуй установленные инструменты проекта; для узкой задачи не добавляй новый стек. По изображениям проверяй только видимые признаки; поведение, семантику, производительность и другие ширины отмечай непроверенными.

## 3. Проверь и воспроизведи

Начни с baseline: основной сценарий, полная страница и ключевые состояния до изменений. Целевые viewport берутся из проекта; при неизвестных начни с 1440×900, 768×1024, 390×844 и около 320 CSS px. Проверь также переходы около реальных breakpoints, zoom, длинные тексты, меню и модальные окна. Эмуляция устройства не доказывает работу на реальном телефоне.

Выполни визуальную, поведенческую и инструментальную проверку по применимым модулям. Для каждого симптома сохрани место, состояние, шаги и доказательство. Если DOM/CSS доступны, измеряй спорную геометрию и computed styles. Не выдумывай точные пиксели/контраст по изображению. Свяжи runtime/network ошибки с конкретным действием и эффектом; шум расширений и warnings не называй автоматически дефектами.

Для отказов сети, 4xx/5xx, загрузки, истёкшей сессии и ролей используй test/staging, существующие mocks и тестовые аккаунты. В обычном UI-ревью не отправляй реальные заявки, не оплачивай и не удаляй реальные данные. Не открывай чужие приватные данные. Непроверяемый сценарий фиксируй как `not_checked`, а не `pass`.

## 4. Покажи интерактивный чек-лист до исправлений

Пользователь должен увидеть конкретный список перед первой правкой. Следуй [контракту отчёта и цикла исправлений](references/report-workflow.md). Сохрани канонический JSON и сгенерируй автономный HTML с помощью `scripts/checklist.py`. Открой/покажи файл доступным инструментом и дай ссылку. В среде без HTML-интерфейса предложи открыть созданный HTML в браузере; не называй обычный список интерактивным.

Каждая находка имеет стабильный ID `UI-001`, тип (`defect`, `hypothesis`, `recommendation`), приоритет, наблюдение, ожидаемое поведение и основание, влияние, доказательство, исправление и критерий повторной проверки. Группируй одну первопричину, отмечай связанные экраны. Приоритет определяется последствиями:
- P0 — подтверждённый критический ущерб/потеря данных; косметика сюда не относится.
- P1 — основной сценарий заблокирован или восстановление невозможно.
- P2 — сценарий затруднён, есть обход; значимая визуальная/адаптивная/доступностная проблема.
- P3 — локальная косметика без препятствия сценарию.

Гипотезы и субъективные рекомендации не исправляй автоматически. Если дефектов нет, всё равно создай отчёт с фактическим покрытием, без выдуманных задач и баллов. Чекбокс «в плане» выбирает работу, а отметка «проверено» отражает доказанный результат; одно не заменяет другое.

## 5. Исправляй и показывай ход работы

После публикации чек-листа продолжай без повторного запроса разрешения, если пользователь не ограничил режим. Выполняй выбранные подтверждённые дефекты по влиянию и зависимостям. Сначала изучи причину и существующие компоненты/токены; затем внеси минимальную устойчивую правку. Не меняй брендинг, архитектуру или чужие изменения ради косметики.

Обновляй JSON и HTML для каждого дефекта или небольшой связанной группы: `open → in_progress → fixed_pending_verification → verified`. До начала покажи ID и план правки; после — что поменялось, где и каким способом проверено. При длительной работе показывай прогресс не реже минуты. Не приравнивай изменение кода к успешной проверке.

Перепроверь исходные шаги на тех же данных, размерах и состояниях, затем соседние viewport и общий компонент на связанных экранах. Покажи «до/после» для визуальных изменений; для поведения — исходный и повторный результат сценария/trace. Для производительности — сравнимые условия и реальные замеры. Добавляй только содержательные тесты для поведения/регрессии, не тесты совпадения CSS с реализацией. Выполни обязательные проверки проекта.

Если повторная проверка провалилась, верни задачу в `in_progress` и исправь причину. Если проверка недоступна после правки, оставь `fixed_pending_verification` с причиной; при отсутствии доступа/решения — `blocked`. Явно исключённая задача — `deferred`. Не ставь «выполнено» заранее и не зависай на одном блокере: продолжай независимые задачи. Завершай после исправления и проверки доступных подтверждённых дефектов; оставшиеся ограничения перечисли явно.

## 6. Итог

Обнови интерактивный отчёт и покажи итоговые отметки, доказательства и изменения. В чате кратко укажи проверенный охват, исправленные ID и оставшиеся непроверенные/заблокированные задачи. Не называй выборочную QA сертификацией WCAG, лабораторный замер — полевым, экспертную гипотезу — доказанной конверсией.

JSON, HTML и изображения храни в согласованном каталоге проекта для артефактов (по умолчанию `.ui-review/<run-id>/`), без секретов и персональных данных. Итог конкретного ревью не сохраняй автоматически в личную базу знаний. Внешние отчёты используют достижимые ссылки и относительные пути. [Источники методики](references/sources.md) читать при уточнении стандартов и инструментов.
