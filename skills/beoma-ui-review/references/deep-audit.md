# Методика глубокой проверки

Применяй базовые модули ко всем экранам, профильные — по типу системы. Глубокое ревью сочетает ручную оценку, выполнение сценариев и инструментальные доказательства. Статический анализ кода дополняет наблюдение в браузере.

## Визуал и дизайн-система

Используй [визуальный чеклист](checklist.md): сетка, baseline, padding, иерархия, typography, контент и states. Сопоставляй реальные размеры, цвета и компоненты с токенами и доступным макетом. Проверяй весь scroll, изображения, обрезание, ретину при доступности данных, загрузку шрифтов и fallback, меню/оверлеи, z-index и sticky.

Для visual regression используй существующие screenshot-тесты и сверку глазами. Стабилизируй viewport, browser/OS, шрифты, данные, clock и анимации; дождись готовности содержимого. До/после должны иметь одинаковое состояние и масштаб. Mask динамических областей оправдан только реальной нестабильностью; не прячь дефект. Pixel diff указывает на изменение, а не сам по себе на ошибку. Не обновляй golden snapshots автоматически, чтобы сделать красный тест зелёным.

## Адаптивность и устройства

Десктоп, планшет, мобильный, узкий экран и breakpoint±несколько CSS px. Проверяй горизонтальную/вертикальную ориентацию, zoom 200%, reflow около 320 CSS px, текстовое увеличение при наличии инструмента. Учитывай исключения WCAG для двухмерного содержимого.

Проверь fixed/sticky, scroll вложенных панелей, safe area, виртуальную клавиатуру при доступности реального устройства, focus под оверлеями, touch-цели и hover-only функции. Повторяй с длинными локализованными строками и большими/нулевыми числами. При поддержке нескольких браузеров проверь доступные Chromium/WebKit/Firefox по конфигу проекта; не объявляй все браузеры проверенными по Chromium или мобильной эмуляции.

## Доступность

Ориентир для глубокой QA — применимые WCAG 2.2 A/AA, если проект не задал иной уровень. Конкретный критерий подтверждай по актуальной спецификации. Сочетай axe/существующий сканер, keyboard walkthrough и проверку accessibility tree. Сканируй раскрытые меню, ошибки и диалоги, а не только первоначальный DOM. Без инструмента отмечай автоматический проход непроверенным.

Проверь labels и accessible names, heading/landmarks, alt, роли/состояния, порядок и видимость focus, отсутствие keyboard traps, возврат фокуса после диалога, skip links при длинной навигации. Контраст измеряй, учитывая alpha и фактический фон. Ошибки/успех должны быть доступны без цвета и при необходимости объявляться assistive technology. Проверь reduced motion и операции, доступные без drag. Для screen reader утверждай только реально проверенные сочетания OS/браузер/AT.

## Сценарии сервиса

Составь карту ключевых маршрутов и пользовательских целей. Пройди вход/выход, onboarding и главное действие в разрешённой среде, если они применимы. Проверяй навигацию, back/forward, прямой URL/refresh, сохранение query/filter/pagination и данных формы. Оцени понятность терминов, статуса системы, отмены и восстановления, без произвольного переписывания UX.

Для форм: empty/invalid/valid, обязательность, формат/границы, paste/autofill, inline/server errors, pending/disabled/success. В тестовой среде проверь double submit и повтор после отказа. В таблицах/поиске — пустой набор, no results, длинные строки, фильтры/сортировка, pagination, stale/partial data. Для ошибок 401/403/404/500, offline/slow response и session expiry — mocks или согласованные тестовые условия; отображение технических деталей и потеря пользовательского ввода являются отдельными наблюдениями.

Общие компоненты проверяй на нескольких типах экранов. Для ролей — только доступные тестовые accounts; это проверка отображения и сценария, не пентест доступа.

## Лендинг и путь к целевому действию

Проверь понятность предложения для целевой аудитории, связь заголовка и CTA, последовательность секций, читаемость выгод/условий и путь к форме/контакту. Выявляй противоречия между обещанием и фактическим действием CTA, ссылки на пустые секции, broken anchors, формы без исхода, перекрытие cookie banner и мобильного CTA. Проверь header/footer, все уникальные CTA и модальные варианты.

Проверь доступность условий, цены и контактов, если они нужны для осознанного действия. Не придумывай отзывы, статистику, скидки, социальное доказательство или нормативные требования. Пожелания к тексту и расположению секций маркируй как рекомендации, пока нет макета/исследования/явного дефекта.

Если доступны тестовая аналитика и разрешённая диагностика, проверь, что событие действительно связано с действием и не дублируется. Не отправляй тестовые лиды в production CRM. Экспертная QA не доказывает uplift: для конверсионных гипотез отдельно нужны исследование пользователей, funnel-данные или эксперимент.

## Производительность и стабильность

При наличии инструментов измерь загрузку, отзывчивость и layout shift. На 2026-10-10 ориентиры Core Web Vitals: LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1; полевое прохождение оценивается по p75 отдельно для mobile/desktop. При использовании позднее перепроверь источник. Без полевых данных не заявляй реальный p75/INP по одному Lighthouse.

Для лаборатории фиксируй tool/version, device/network/CPU, cold/warm cache, URL, действия и число прогонов; сравнивай до/после одинаково, объясняй разброс. TBT и score не равны полевому INP. Проверь видимые jumps от шрифтов/изображений, размер hero, загрузку критических ресурсов, блокирующие скрипты и долгие реакции основного сценария. Не оптимизируй произвольный балл ценой дизайна или функций.

## Runtime, контент и публичная выдача

Свяжи console errors, failed requests, hydration issues, 404 assets и broken links с воспроизводимым пользовательским эффектом. Проверяй доступные метаданные ошибок без сохранения auth headers/cookies/PII. Не воссоздавай падение backend воздействием на production.

Для публичного лендинга проверь title, meta description, понятные ссылки, семантическую структуру и доступность основного контента. При явном SEO-охвате — canonical/indexability/robots по назначению страницы; staging/private service не должны индексироваться автоматически. OG/social preview проверяй при его применимости. Не обещай позиции в поиске.

## Регрессия после исправления

Повтори исходный сценарий в идентичных условиях, затем связанные состояния/маршруты и соседние ширины. Проверь keyboard/focus после перемещения элементов. Для общей CSS/компонентной правки расширь выборку до всех затронутых типов компонентов. Выполни существующие build/lint/typecheck/test по инструкциям проекта, добавляя тесты лишь для существенного поведения. В итоговом покрытии отмечай только реально выполненные проверки.
