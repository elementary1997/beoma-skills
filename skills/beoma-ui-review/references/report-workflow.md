# Интерактивный чек-лист и цикл исправлений

## Файлы и источник истины

В потребителе создай `.ui-review/<run-id>/state.json`, `report.html` и при необходимости `images/`. Используй каталог артефактов проекта, если он уже задан. Конкретные отчёты не входят в библиотеку скиллов и не отправляются автоматически в Git. `state.json` — технический источник истины; HTML — представление. Не сохраняй session tokens, cookie/headers или персональные данные в артефактах.

Вызов скрипта делай относительно установленного скилла, а не угадывай глобальный путь:

```sh
python3 <skill-dir>/scripts/checklist.py render --state .ui-review/<run-id>/state.json --output .ui-review/<run-id>/report.html
```

Заменяй обозначения `<...>` реальными путями. Положи HTML рядом с JSON; изображения указывай относительно HTML, например `images/UI-001-before.png`. Абсолютные локальные пути и `../` не используются для встроенных картинок. HTML автономен, без CDN, сетевых API или необходимости npm. При отсутствии Python используй имеющиеся инструменты, чтобы воспроизвести этот контракт и HTML-шаблон; сообщи, если генерацию не удалось выполнить.

Открой готовый HTML доступным инструментом среды и покажи ссылку **до первой правки**, затем сразу продолжай выбранные подтверждённые дефекты. Обновляй JSON и повторно генерируй HTML после изменения статуса/доказательств. Покажи актуальную ссылку и скриншоты до/после; пользователь перезагружает открытый отчёт, чтобы увидеть новую версию. Не утверждай наличие автоматической live-синхронизации.

## Контракт JSON

- `run_id`: уникальная строка, не переиспользуемая для другого аудита; `title`: название системы/экрана.
- `scope`: непустой список фактически проверенных URL, состояний, browser/version, viewport, среды и ограничений.
- `coverage`: непустой список объектов `check`, `result`, `evidence`. Результаты: `pass`, `fail`, `not_checked`, `not_applicable`. Evidence описывает доказательство либо причину пропуска/неприменимости.
- `issues`: список находок, допустим пустой, если есть покрытие.
- `review_decisions`: необязательный объект выбора пользователя по ID: `{ "UI-001": { "selected": true, "note": "..." } }`.

Находка:

```json
{
  "id": "UI-001",
  "kind": "defect",
  "priority": "P2",
  "status": "open",
  "title": "Краткое название подтверждённой проблемы",
  "location": "URL, viewport и состояние",
  "observation": "Что реально наблюдалось",
  "expected": "Что должно происходить",
  "basis": "Макет, токен, требование или обоснованный принцип",
  "impact": "Последствие для пользователя",
  "before": ["images/UI-001-before.png", "Шаги и измерение до правки"],
  "fix": "Минимальная правка",
  "retest": "Сценарий и ожидаемый исход повторной проверки"
}
```

Не подставляй пример в реальный отчёт. `kind`: `defect`, `hypothesis`, `recommendation`. Для подтверждения гипотезы обнови `kind` и доказательства после проверки, затем решай исправление. Рекомендации не становятся дефектами от выбора чекбокса.

## Технические статусы

- `open`: найдено, код не исправлен.
- `in_progress`: исправление началось; сначала покажи ID пользователю.
- `fixed_pending_verification`: код изменён, `change` описывает файлы и исправление; успешный повторный прогон ещё не подтверждён.
- `verified`: есть `change`, непустой `after` и `verification` с `result: "passed"`, `method`, `environment`, списком `evidence`. Для визуальных дефектов нужны реальные снимки до/после либо доступные пользователю ссылки; если нет возможности их показать, обозначь ограничение и не заявляй визуальный прогон.
- `blocked` / `deferred`: обязательный `reason`. Код не изменён или работа/проверка остановлена; объясни конкретно.

При провале повторного прогона верни задачу в `in_progress`. При отсутствии проверки после правки сохрани `fixed_pending_verification` и причину. Повторно открытый дефект переводится из `verified` в `in_progress`. Счётчик завершения учитывает только `verified` среди подтверждённых дефектов, независимо от пользовательских галочек.

Можно редактировать JSON обычным файловым инструментом с последующей валидацией при render. Для контроля переходов предпочтителен patch:

```sh
python3 <skill-dir>/scripts/checklist.py patch --state .ui-review/<run-id>/state.json --id UI-001 --patch /path/to/patch.json
```

Patch содержит только изменённые поля. Например `{"status":"in_progress"}`, затем `{"status":"fixed_pending_verification","change":"..."}`, затем реальную верификацию и `after` вместе со статусом `verified`. Скрипт записывает историю переходов и не допускает verified без необходимых полей. Наличие полей само по себе не доказывает истинность данных: агент отвечает за реальный прогон.

## Выбор пользователя и ограничения интерактивности

HTML позволяет фильтровать и раскрывать находки, выбирать задачи «в плане» и оставлять заметки. Техническая галочка «исправлено и перепроверено» доступна только для чтения. Выбор хранится в browser localStorage (если доступно); он не меняет source JSON и не отправляет сообщения агенту.

Чтобы передать выбор агенту, пользователь экспортирует `ui-review-decisions.json` и предоставляет этот файл в сессии. Если он уже сообщил выбор в чате, сразу отрази его в JSON. Экспорт из другой run_id отклоняется. Импортируй только пользовательский выбор и заметки:

```sh
python3 <skill-dir>/scripts/checklist.py import-decisions --state .ui-review/<run-id>/state.json --decisions /path/to/ui-review-decisions.json
```

Импорт не может присвоить `verified` или поменять evidence. Исключённые ещё не начатые задачи обозначь `deferred` с причиной; текстовые ограничения пользователя имеют приоритет. Пока выбора не было, выполняй подтверждённые дефекты по умолчанию; не делай лишнюю паузу после публикации чек-листа. Будь честен: локальная галочка без экспорта или сообщения в чат не управляет работающим агентом в реальном времени.
